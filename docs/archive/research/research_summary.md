# AIC 开源调研决策摘要

核验日期：2026-10-08（Asia/Shanghai）。本轮调查 14 个候选，深入比较 6 项，读取代表源码、依赖、根许可和提交／发布记录；产出 7 个专项机会。没有开发、Fork、安装参考依赖、运行上游测试或发布仓库。所有技术结论均有静态检查边界，没有实测学习效果。

## 1. 先处理时间约束

本地未发现用户指定的《AIC_AI开源比赛指导文档_2026 (1).md》，采用提示词原则并取得官网通知及两份附件。**官网初赛作品提交截止为 2026-10-15 20:00，距核验日约一周；2～4 周不能直接视为本届剩余开发窗口。** 初赛作品截止后不可修改，复赛主要是评审，后续更新应以明确通知为准。[官方通知](https://www.aicomp.cn/tracks/tracks-5/4924.html)

官方六项评分权重与用户给定一致。更值得投入的是小场景、真实闭环、自主机制和可核验对照，而不是增添功能或模型训练。上游测试存在、模型解释流畅、页面漂亮都不能独立证明学习提升。

## 2. 最值得参考的三个开源项目

| 项目 | 为什么优先 | 建议使用方式 |
|---|---|---|
| [CodeHelper Studio](https://github.com/SuLiverse/CodeHelper-Studio) | Windows 桌面、编辑／运行、错题、SM-2、AI 和本地数据流程齐，便于研究可复用闭环 | 条件性 Fork／有限原型；固定 `23773e8` 后再验证运行 |
| [Pyodide](https://github.com/pyodide/pyodide) | Python 浏览器运行时可降低服务端和宿主工具链成本，模块边界独立 | 消费稳定发布运行时；自行做判题／证据／超时协议 |
| [ts-fsrs](https://github.com/open-spaced-repetition/ts-fsrs) | 排程和日志类型成熟，TS 集成较小，不要求模型训练 | 只用 scheduler；独立掌握机制与排程分别设计 |

这三个按“可运行底座与小模块”优先级选出，不是教学创新或产品质量排名。**机制方面继续看 OpenTutor、SmartCode 和 EduTelligence／Iris**：它们已有真正的教学状态、评价和提示设计，也暴露了本作品应避免重复包装的能力。[评分与源码依据](<project_comparison.md>)

## 3. CodeHelper 是否值得 Fork

**有条件值得；本轮不建议立即决定正式底座。** 它已实现“失败提交→错题→SM-2 排程”，不是只有界面；MIT 许可有利于合法二次开发；当前发布有 Windows 安装版和 Portable。

关键不足是：复盘入口主要提供标题、错误类型、标签与代码，未加入真实失败用例；mastered 使用 `repetitions >= 3`，由自评驱动；未在已检查核心路径发现经验证的跨题误解与独立迁移验收。SQL 提交比较规范化文本，也不是执行结果集判题。[完整分析](<codehelper_deep_analysis.md>)

下一轮可先验证目标 Windows 的原基线和一个新入口。如果 1～2 天内能贯通提交、错题、证据落表，继续专项改造；如果成本主要耗在原生 ABI、打包或全局状态耦合，独立 Python 小应用更适合。初期隐藏课程、宠物、成就等入口；彻底删依赖必须等核心闭环确认后。

## 4. 最值得复用的模块

- **直接能力：** CodeMirror 编辑器、CodeHelper 的 IPC／AI 请求取消／SQLite 备份边界；或独立应用中的 Pyodide 执行。
- **成熟学习基础：** 已有 SM-2 作为对照；独立项目的 ts-fsrs 排程和日志。先不做深度知识追踪训练。
- **教学机制参考：** SmartCode 的实际运行覆盖模型判决；OpenTutor 的 BKT／Socratic 状态与诊断协议；Iris 的不泄题合约。
- **可授权内容与测试：** 少量核验后的 Exercism Python 概念题和边界测试，以及自己的题、误解标签和验证案例。

推荐候选组合为 **有限 CodeHelper 原型**，或 **独立 React／TS＋Pyodide＋小题集＋可选 ts-fsrs**。不会同时部署所有平台。[三条路线及兼容性](<reuse_strategy.md>)

## 5. 已有功能不能再作为创新

自动收集错题、自由文本 AI 分析、SM-2／FSRS、自评、三级提示、RAG、本地数据、Agent 工具调用、一般技能评分、结构化错误分类、同概念派生题、提交 diff 复盘，都已有本轮候选实现或明确提示入口。

可归属改进应是“哪条证据能核验诊断”“如何区分辅助完成与独立掌握”“生成题为什么可接受或应拒绝”等具体机制，加上对照数据。没有把调用通用 API 包装成算法突破。

## 6. 三个最值得继续验证的专项方向

| 机会 | 核心动作 | 优先证明什么 |
|---|---|---|
| 错因验真台 | 保存失败输入／输出，AI 提出假设，重跑核验并追问确认 | 诊断是否更准确、无证据断言是否更少 |
| 同错因迁移训练 | 跨题确认同一误解，再做新任务 | 新题一次通过与解释是否改善，不能只重做原题 |
| 独立掌握检查站 | 记录 AI 辅助，安排无辅助新题，分别统计 | 是否减少“自评掌握却不会独立做”的漏检 |

另有不泄题提示审计、SQL 等价诊断、变式题质检、AI 小改动回归验收四个备选。每项包含用户操作、已有／自研／假设边界、最小 Demo、失败风险和对照方法。[七项机会](<project_opportunities.md>)

如果只有一周且找不到真实学习者，优先证明工程／诊断效果；SQL 或变式质检可能更容易得到客观对照。没有长期数据时，不宣称学习保持提升。

## 7. 主要未知风险

| 风险 | 下一步应取得的证据 |
|---|---|
| 本届初赛时间与资格 | 确认实际报名／提交状态、是否符合官方学生资格，以及后续通知 |
| Windows 可运行性 | 原基线、锁定版本、目标工具链、打包和数据恢复；本轮未实测 |
| 错因标签可靠性 | 少量真实错误代码与可核验标注；程序症状不能直接推断人的误解 |
| 用户与学习效果 | 可接触学习者、等难度未见题、提示记录和实际时间窗口 |
| API 与本地模型成本 | Provider／模型／配额、用量与延迟；没有承诺本地模型免费且好用 |
| 资源许可 | 外部题面、依赖、素材、数据和模型分别确认；根 MIT 不包办全部权利 |
| 版本与文档漂移 | CodeHelper 的旧索引／重定向；Pyodide 的不同版本线；按固定快照复查 |

许可重点：Pyodide 为 MPL-2.0，不能把组合统称全 MIT；Judge0 为 GPL-3.0；Dify 带多租户和前端标识附加限制，排除自由改名分发底座推荐。详细使用边界见路线报告。

## 8. 下一轮最应解决的问题

按顺序明确：**本届一周截止是否是硬目标→语言与一个真实用户场景→能取得哪些案例和评审者→先证明诊断还是学习效果→再选架构。** 用前两项机会各 3～5 个真实案例判断是否有必要，并验证原基线成本后，再决定 Fork 或独立实现。
