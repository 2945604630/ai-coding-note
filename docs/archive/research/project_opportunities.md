# 专项选题机会：七个可继续验证的方向

核验日期：2026-10-08（Asia/Shanghai）。以下是基于实际源码发现的机会，不是已决定的选题、已实现功能或已证实创新。已有能力与代码证据见 [候选池](<open_source_candidate_pool.md>)、[CodeHelper 分析](<codehelper_deep_analysis.md>)和 [横向比较](<project_comparison.md>)。

## 1. 先排除不能重复包装的功能

CodeHelper 已有错题收集、AI 复盘、SM-2、自评、上下文辅导、同类训练题／最小反例快捷提示、本地检索和 Agent 审计。SmartCode 已有三级提示、技能评分、选题及真实运行覆盖模型判决。OpenTutor 已有 BKT、结构化错因、同概念派生题和苏格拉底状态机。Iris 已有不泄题提示阶梯和审查；CF Compass 已有提交时间线和 diff 证据化复盘。

因此，“大模型分析错题”“个性化推荐”“生成变式”“知识图谱”“三级提示”“带 diff 的复盘”都不能单独当作本作品新机制。机会应落在**真实证据约束、行为确认、生成结果验收、独立迁移验证和可复用评测**。即使存在这些改进，也不宣称全球首创或算法突破。

## 2. 七个具体机会

### 机会 1：错因验真台——让 AI 的诊断可以被反例检验

1. **可能名称：** 错因验真台。
2. **用户：** 学 Python 循环、条件和列表的初学者，以及帮他们审阅代码的助教。
3. **具体问题：** AI 能说“边界错了”，却不给能重现的证据；同一报错也可能只是输入格式问题，学习者不知道建议是否可信。
4. **操作场景：** 用户提交“求列表最大值”代码；系统执行后保存失败输入，例如全为负数的数组。AI 提出“初值假设可能错误”和一个追问；系统将它引用的用例重跑，必要时缩小输入；用户说明为什么设初值为 0，再做一份新输入验证。
5. **参考资源：** CodeHelper 的提交／错题和 AI 入口、SmartCode 的真实执行覆盖模型判决、Pyodide 的 Python 运行时。输入缩减从小型整数列表开始，不做通用程序分析器。
6. **核心 AI 能力：** 依据题意、代码和真实输出提出有限诊断假设、给出区分假设的追问，并引用有效证据 ID。AI 不决定用例实际通过与否。
7. **自主机制与假设：** 自主开发“假设→证据→追问→确认／待定”的状态；限制 AI 的无证据断言，校验引用与实际运行。**待验证假设：** 相比同模型自由文本复盘，错误诊断和不可重现断言更少。错误程序并不必然说明用户持有某种误解，必须保留“尚未确认”。
8. **最小 Demo：** 5～10 道整数／数组小题、确定性执行、结果保存、一类诊断 JSON、证据校验、一个追问、前后结果导出。先只有一个错误族也可形成流程。
9. **最易失败：** 模型给出的“根因”仍可能只是程序症状；生成反例的 expected 本身错；缩减破坏输入前提。通过人工参考实现和输入校验控制范围。
10. **证明改进：** 固定 30～50 个错误程序与 10～20 个正确程序，包含同症状不同错因；由能核验代码的人标注。与原 CodeHelper quickAsk／无证据 LLM、纯执行报告分别对照，统计诊断正确率、无证据断言率、反例复现率、拒绝不确定诊断的比例。先验证工程和诊断效果，学习提升需另做用户实验。

**边界归属：** 已有＝执行、错题、模型调用；计划自研＝证据协议、核验器和追问确认；待验证＝减少错因误判。工时推断 2～3 周，一周仅做单错误族，不含长期教学验证。

源码起点：[CodeHelper 复盘提示构造](https://github.com/SuLiverse/CodeHelper-Studio/blob/23773e843d2a7bc3b04eedff59055b6c3a7afe7b/src/views/ReviewView.tsx#L255-L286)、[SmartCode 执行覆盖](https://github.com/mohddarwix/SmartCode/blob/8b7a3e56bb64067ded83bf7ebd0a1e93ba65d70d/backend/app/llm/submission_evaluator.py#L199-L340)。

### 机会 2：同错因迁移训练——区分“修好这题”和“理解这个概念”

1. **可能名称：** 同错因迁移训练。
2. **用户：** 多次在不同题目上犯相似错误的 Python 入门学习者。
3. **具体问题：** 按题目保存错题难以发现共同误解；两题都 WA 不代表同一原因，重复原题又可能靠记答案通过。
4. **操作场景：** 用户在二维列表初始化和复制列表题上分别失败。AI 根据代码和一个诊断问题怀疑“别名共享”误解；用户完成小型状态预测题后，系统推荐不同故事背景的独立编程题，检查是否会应用正确概念。
5. **参考资源：** OpenTutor 的错因分类／诊断题／BKT，Exercism Python 的概念测试，CodeHelper 的提交记录。不需要深度知识追踪训练。
6. **核心 AI 能力：** 将现有证据映射到预设 6～10 个细粒度误解，选择能区分原因的追问或验证题；解释两次错误为什么可能相关。
7. **自主机制与假设：** 自研跨题“误解假设”记录，按用户回答确认，而不是按 tags 或 WA 聚类；新题由固定模板＋经测试的参数变式提供。**待验证假设：** 同样训练时间下，跨题验证比重做原题更能暴露未掌握概念。BKT、同概念派生题本身都不是新点。
8. **最小 Demo：** 三个错误族、每族原题／追问题／迁移题各一组，历史关联、独立作答与结果报告。先用明确映射，不建巨大知识图谱。
9. **最易失败：** taxonomy 太粗、题目同时考多概念、迁移题难度不等；将表面相关当认知原因。需保留不同原因对照和多概念限制。
10. **证明改进：** 工程阶段检查跨题分组与人工标注一致性；用户阶段比较“原题重练”和“诊断＋迁移”，固定总练习时间，以未见题一次通过率、解释正确性和提示次数评价。小样本交叉顺序应平衡，结果只报告试验范围。

**边界归属：** 已有＝BKT、结构化分类、派生题；计划自研＝程序误解证据模型、确认规则、执行合格的迁移题；待验证＝迁移效果。预计 3～4 周，一周只能展示一个概念的技术闭环。

源码起点：[OpenTutor classifier](https://github.com/zijinz456/OpenTutor/blob/5fea390a49be81827342caa19846fecbcf147e4a/apps/api/services/diagnosis/classifier.py)、[现有派生题](https://github.com/zijinz456/OpenTutor/blob/5fea390a49be81827342caa19846fecbcf147e4a/apps/api/services/diagnosis/derive.py)。

### 机会 3：独立掌握检查站——检查用过 AI 后是否还能自己完成

1. **可能名称：** 独立掌握检查站。
2. **用户：** 已依赖 AI 完成代码、但想知道自己学会没有的学习者。
3. **具体问题：** 看懂提示、复制修复、点击“已掌握”容易得到积极记录；一次 AC 无法区分辅助完成与独立理解。
4. **操作场景：** 用户借 AI 修好循环题，系统记录提示次数和辅助状态。下一步收起答案，给一个数据和背景不同的短任务：先预测结果，再独立改／写代码。通过后才记为独立验证；失败回到证据诊断。
5. **参考资源：** CodeHelper 自评／review_schedule，ts-fsrs，TuTor 的学生操作与只读确认规则，Exercism 小题测试。
6. **核心 AI 能力：** 根据用户用了哪些提示选择检查题和追问，评阅自然语言解释时给明确证据；程序正确性由运行器判定。
7. **自主机制与假设：** 区分“辅助完成／原题独立／新题独立／延迟保持”的状态，题目评分和复习排程分开；只有符合独立条件的观测进入相应指标。**待验证假设：** 能减少“自评掌握却新题失败”的漏检。不能保证用户不在另一个窗口使用 AI，单用户产品依赖诚实模式和记录。
8. **最小 Demo：** 一个概念，提示日志、原题通过、新题独立检查、状态转换、复习安排和结果导出；不做摄像头监考或复杂防作弊。
9. **最易失败：** 验证题不等难度、额外作答让用户退出、提示日志漏记、用户外部辅助；这些都要在解释结果时记录。
10. **证明改进：** 对照“自评即可掌握”的 CodeHelper 基线，测已掌握用户的新题失败比例、漏检率、提示依赖和完成时间。若有窗口再进行 3／7 天复测；一周提交只能报告已取得的短期结果，不能虚构保持提升。

**边界归属：** 已有＝自评、调度、逐步教学；计划自研＝独立条件协议、观测状态和检测流程；待验证＝掌握识别质量。预计 2～3 周，一周可做一个概念，但不一定能获得充分用户样本。

源码起点：[CodeHelper 的 mastered 统计](https://github.com/SuLiverse/CodeHelper-Studio/blob/23773e843d2a7bc3b04eedff59055b6c3a7afe7b/electron/ipc/review.ts#L198-L238)、[ts-fsrs 日志类型](https://github.com/open-spaced-repetition/ts-fsrs/blob/c8ca282edc3fe1cdfa1c24912437938b63a25cb3/packages/fsrs/src/models.ts)。

### 机会 4：不泄题提示审计官——验证提示是否真的帮助思考

1. **可能名称：** 不泄题提示审计官。
2. **用户：** 给编程课配置 AI 助教的老师，以及需要自己练习的学生。
3. **具体问题：** 提示常直接写出修复，学习者得到答案却没有完成判断；仅在 prompt 中禁止给答案无法确认是否遵守。
4. **操作场景：** 用户在二分边界出错。AI 首次只指出失败测试和需检查的决策；学生先预测执行过程，再请求下一层。系统检查生成提示是否带完整修复、能否直接照抄通过，并记录人工复核。
5. **参考资源：** Iris 的 non-spoiler contract／review 模板、SmartCode hint_level、TuTor 的一步验证。
6. **核心 AI 能力：** 生成有定位依据的分层提示；审阅提示是否包含解决方案，结合规则与人工评估。
7. **自主机制与假设：** 自研中文 Python 场景下的提示审计集、可复制修复检测和“先回答再升级”交互。**待验证假设：** 在固定提示预算下，减少答案泄露同时维持解题完成率。三级提示和 non-spoiler 合约已有，不能再声称原创。
8. **最小 Demo：** 10 道小题、三层提示、学生响应、规则检查、提示审阅记录和泄题案例回放。
9. **最易失败：** LLM 审 LLM 互相认可；直接抄代码检测抓不到语义泄题；限制过严使提示没用。须保留人工双人标注而非只使用模型分数。
10. **证明改进：** 固定提示请求和代码，比较普通提示与审计流程；测人工定义的完整／近完整答案泄露率、下一次独立修复率、错误提示率、延迟和调用量。至少重复模型生成，报告评审一致性。

**边界归属：** 已有＝分层提示／审查；计划自研＝专项基准、审计器与行为门槛；待验证＝泄题／完成率权衡。预计 2～3 周；适合形成开放测试集，单独的“换中文 prompt”不足以参赛。

源码起点：[Iris 提示阶梯合约](https://github.com/ls1intum/edutelligence/blob/4065add4b76b2edd283f35e31d5ac620f477077e/iris/src/iris/pipeline/prompts/templates/struggle_hint_contract.j2)。

### 机会 5：SQL 等价诊断实验室——用结果区别写法和语义错误

1. **可能名称：** SQL 等价诊断实验室。
2. **用户：** 练习 SQLite 查询、GROUP BY 和 JOIN 的初学者。
3. **具体问题：** SQL 文本不同可能结果等价；样例相同也可能只是数据碰巧未暴露 NULL、重复或连接错误。CodeHelper 的 SQL 题库提交当前比较规范化文本。
4. **操作场景：** 用户写 JOIN 查询，系统在固定小数据库上执行用户／参考查询，显示差异行。AI 判断可能是连接条件或聚合误解，提出补充数据场景；系统用人工验证的 fixture 检验，再给改换表结构的练习。
5. **参考资源：** CodeHelper 的内存 SQL runner、现有判题接口；保留 SQLite，不扩成支持所有数据库的平台。
6. **核心 AI 能力：** 根据结果差异解释错误，并提出能区分查询行为的 fixture／追问。执行、比较和 fixture 合法性由程序验证。
7. **自主机制与假设：** 自研明确的行序／多重集／NULL／数值规则、差异证据和经验证的诊断数据。**待验证假设：** 相比文本判题，降低等价 SQL 误拒并暴露样例巧合通过。结果判题已有成熟方法，不称为新算法；价值在针对初学者的诊断闭环。
8. **最小 Demo：** 只允许 SELECT 的 SQLite 子集，三类查询、固定 fixtures、结果比较、AI 解释和对照报告。
9. **最易失败：** 认为所有输出都无序、错误处理重复值和 NULL、有限数据误证明普遍等价、混用 SQL 方言。只能说明在测试数据上等价，不宣称形式证明。
10. **证明改进：** 20 组等价写法＋20 组确有错误的查询，包含 ORDER BY、重复和 NULL；与原文本判题比误拒／误接收，另评诊断正确性。AI 去掉后用纯结果报告作消融，证明解释／追问是否有实际价值。

**边界归属：** 已有＝SQL 执行器；计划自研＝结果判题、fixture 验收和教学诊断；待验证＝错误识别与解释质量。预计 2～3 周；一周可限一种 JOIN 错误，工程比跨题认知模型更确定。

源码起点：[现有 SQL 文本判题](https://github.com/SuLiverse/CodeHelper-Studio/blob/23773e843d2a7bc3b04eedff59055b6c3a7afe7b/electron/ipc/problems.ts#L151-L166)。

### 机会 6：变式题质检工坊——拒绝“能输出 JSON 但题目无效”

1. **可能名称：** 变式题质检工坊。
2. **用户：** 为入门编程准备练习的助教、自学者和小型教学应用开发者。
3. **具体问题：** AI 生成题可能题面／答案／测试不一致，或者只是换数字；错误题会反过来误导学习者。
4. **操作场景：** 用户选“空列表处理”概念，AI 生成题面、参考实现、starter 和测试。系统运行参考实现应通过，starter 应在指定错误上失败，几份固定错误程序也应被测试抓住；没有通过验收的题放入待审核区。
5. **参考资源：** OpenTutor derive 的同概念变式元数据、Exercism 的 exemplar／tests、Pyodide；Artemis 当前发布说明也已有参考解／starter 的生成校验，因此不把它当全新机制。
6. **核心 AI 能力：** 根据错误族设计变式和解释概念保持依据；根据验收反馈修订，设置有限重试。
7. **自主机制与假设：** 自研小错误族的已知错误程序库、目标缺陷检出和概念保持人工检查，生成结果按质量闸门开放。**待验证假设：** 与只验 JSON 的生成流程相比，进入题库的有效题比例提高。普通“参考解能过”单项检查不够区别已有平台。
8. **最小 Demo：** 两种题模板、20～30 次生成、参考解／starter／错误程序执行、接受／拒绝原因和题包导出。
9. **最易失败：** 参考解和测试由同模型生成，会共享错误；错误程序库太窄，只杀死一个人为缺陷。需独立参考实现／固定人工例和新缺陷对照。
10. **证明改进：** 同模型、同次数、相同预算生成；比较无闸门与闸门的人工有效题率、目标错误检出率、漏放无效题率、保留率和额外调用成本。不能只报告通过闸门后样本，也要报告被拒绝数量和重试。

**边界归属：** 已有＝派生题和部分平台的生成执行校验；计划自研＝专项缺陷库、质量评测和开放题包协议；待验证＝更可靠题库。预计 2～4 周，一周做两模板的批次质检较可控。

源码起点：[OpenTutor 的 JSON／默认值与落表](https://github.com/zijinz456/OpenTutor/blob/5fea390a49be81827342caa19846fecbcf147e4a/apps/api/services/diagnosis/derive.py#L123-L165)、[Artemis 发布说明中的变式校验](https://github.com/ls1intum/Artemis/releases)。后一项仅核对官方发布文档，本轮未深入审计 Artemis 实现。

### 机会 7：AI 小改动回归验收助手——帮初学者核验 Agent 的补丁

1. **可能名称：** AI 小改动回归验收助手。
2. **用户：** 使用 Coding Agent 改小型 Python 函数、但不擅长判断补丁质量的初学者。
3. **具体问题：** Agent 修好当前样例后，可能破坏其他输入；用户只看 AI 的“已修复”说明，缺少可重放证据。
4. **操作场景：** 用户提供函数修改前后版本和需求，系统跑原测试。AI 根据 diff 建议边界反例；独立参考／人工 fixture 验证 expected，系统运行新旧版本对比，再让用户确认行为变化属于修复还是破坏。
5. **参考资源：** CF Compass 的相邻提交 diff 展示、CodeHelper 的 runner 和审计、Pyodide 的执行、Exercism 边界测试组织。
6. **核心 AI 能力：** 解释 diff 对行为的影响，提出新增回归用例和可理解的验收问题；不自动改仓库或把模型说明当测试结果。
7. **自主机制与假设：** 自研“小函数补丁→经独立核验反例→旧／新对照→需求确认”报告和回放包。**待验证假设：** 比仅跑原样例能发现更多回归且减少误报。一般自动测试生成已有，差异要落在初学者可核验流程和小范围缺陷集。
8. **最小 Demo：** 纯函数 Python、两版本输入、固定需求、原测试＋AI 提议测试、验收／待定状态和导出报告；不支持任意项目构建。
9. **最易失败：** 模型将应改变的行为误报为回归；expected 直接来自旧版本而把旧 bug 当正确答案；复杂环境无法重放。只用有明确参考行为的小函数。
10. **证明改进：** 人工构造／核验 20～30 组真修复、带回归补丁和无害重构；比较原测试、普通 AI 测试生成、新流程的回归检出率、误报率、解释可核验率、人工验收耗时。报告每类混淆和无法判断的样本。

**边界归属：** 已有＝diff 证据、执行与测试组织；计划自研＝期望行为核验、需求确认和补丁对照协议；待验证＝回归发现效果。预计 2～3 周；是一条方向 B 机会，不必继续做错题本。

## 3. 哪三项最值得继续讨论

| 机会 | 优先理由 | 当前最大阻碍 | 一周可做的范围 |
|---|---|---|---|
| 错因验真台 | 最直接补 CodeHelper 的复盘证据缺口；工程效果可较快测 | 可靠错因标签和反例 expected | 一个错误族＋小型固定案例＋基线 |
| 同错因迁移训练 | 直面“不同题背后同一误解”，专项学习价值强 | 题目等难度、用户与标签 | 一个概念的确认和新题验收；不声称普遍学习提升 |
| 独立掌握检查站 | 对 Coding Agent 使用者有具体价值；区别辅助完成与独立掌握 | 真实用户与独立条件可信度 | 提示记录＋一份新题＋短期结果 |

这是继续验证的优先顺序，不是最终选择。若本届初赛时限最重要且没有可接触学习者，SQL 判题或变式质检可能更易形成客观工程对照；不会因为学术名词更响亮就优先选择认知模型。

## 4. 公共验证要求

先分清三类结论：**工程正确性**（结果可重跑、状态可恢复）、**诊断有效性**（与人工证据和标注一致）、**学习改善**（真实学习者在未见题或延迟测试的行为）。第一类通过不能推出第三类。

- 在开发前确定题族、样本来源、正确程序和反例，记录题／模型／prompt／运行时版本。训练、调试和验收题按题族分离，防止同模板换数字造成泄漏。
- 对生成式部分，每个样本至少考虑多次独立生成；记录失败、空输出、超时、重试、token 和延迟。相同模型与预算对照才能解释流程改进。
- 保留正确程序与“证据不足”案例，测误报；不要只测试故意有错的代码。AI 自报 confidence 不能作为诊断正确的标签。
- 学习试验可先 5～10 人探索，平衡练习顺序与难度、记录先验经验；样本不足时只报告个案／探索结果和不确定性，不宣称显著或长期提升。
- 若没有能审核的标注者，只能先报告工程指标、用例复现和错误发现；不能由作者或同一模型自评代替可信错因／学习评测。
- 对照至少含现有功能基线及移除关键新机制的版本。例如诊断工具比较无证据 LLM 与执行证据流程，独立掌握工具比较自评与新题验收；不把外观不同当因果变量。

这些为拟议测试设计，**本轮没有实验样本、实测准确率或用户学习增益**。
