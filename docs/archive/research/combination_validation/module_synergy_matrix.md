# 七项功能组合必要性与模块边界

日期：2026-10-08。以下是设计判断，不是合并后的实测收益。评判依据是额外用户价值、必要数据依赖、错误传播风险和维护成本；截止时间不参与判断。已有机制证据详见[重叠审查](<innovation_overlap_audit.md>)。

## 1. 功能定义与关系矩阵

① 证据驱动错因诊断；② 同错因迁移训练；③ 独立掌握检查；④ 不泄题分层提示；⑤ SQL 等价诊断；⑥ 变式题质量验证；⑦ AI 小补丁回归验收。

**高＝高度互补；部＝部分互补；低＝低关联；禁＝不建议在本轮同一产品主线合并；重＝功能重复。** “高”不表示必须整仓部署在一起；“禁”不是任何场景都不能连接。七项整体职责不同，没有需要标为“整体功能重复”的一对；①⑥⑦的反例／测试执行、②⑥的目标映射有明显局部重复，应抽成共享能力。强行给某一整对标“重复”会掩盖其不同验收对象。

| 功能 | ① 诊断 | ② 迁移 | ③ 独立 | ④ 提示 | ⑤ SQL | ⑥ 题质检 | ⑦ 补丁验收 |
|---|---|---|---|---|---|---|---|
| ① 诊断 | — | 高 | 高 | 高 | 部 | 部 | 部 |
| ② 迁移 | 高 | — | 高 | 部 | 低 | 高 | 禁 |
| ③ 独立 | 高 | 高 | — | 部 | 低 | 部 | 禁 |
| ④ 提示 | 高 | 部 | 部 | — | 低 | 部 | 禁 |
| ⑤ SQL | 部 | 低 | 低 | 低 | — | 低 | 部 |
| ⑥ 题质检 | 部 | 高 | 部 | 部 | 低 | — | 部 |
| ⑦ 补丁验收 | 部 | 禁 | 禁 | 禁 | 部 | 部 | — |

## 2. 全部 21 对的理由、收益和代价

| 功能对 | 判断 | 合并产生的额外价值 | 必须传递的信息与边界 | 复杂度是否值得 |
|---|---|---|---|---|
| **①＋②** | 高 | 训练依据确认后的误解，而不是把所有 WA／同标签错误混成一族；纠正诊断可撤销错误推荐 | 传 `confirmed_gap`、概念版本、支持／反证与确认范围；②不得消费仅有 LLM confidence 的假设 | 对 A 值得；前提是误解追問能区分原因。若准确性不如人工选择概念，合并收益消失 |
| **①＋③** | 高 | 新题失败能反证原诊断；原题修复与概念观测分开，形成纠错回路 | 共享 learner、concept、attempt 与证据 ID；③返回观测，不能直接把未通过解释成原误解必然存在 | 对 A 值得；额外成本是事件资格检查与可撤销状态，而非复杂追踪模型 |
| **①＋④** | 高 | 提示只引用有效事实，按待定假设问能区分原因的问题；避免自信但错误地教学生 | ④读取核验后的事实和诊断状态，记录暴露内容；提示泄露检查是独立策略 | 对 B／A 值得；最低配可用固定追问，动态三级提示仍可删。Iris 已有提示契约与锚点校验，不能重复报创新 |
| **①＋⑤** | 部 | 通用证据协议可以承载 SQL 反例，替换 CodeHelper 当前文本归一化比较 | SQL 需独立数据库夹具、方言、NULL、重复行、排序与 bag/set 语义，不能复用 Python stdout 判等当等价证明 | 仅明确服务 SQL 用户时值得；对当前 Python 主线新增执行语义成本超过收益，作为日后插件 |
| **①＋⑥** | 部；局部重 | 同一执行协议支持诊断反例与题目测试；合格题可用于追问 | 共享执行、输入约束、预言机来源；①核验诊断，⑥核验题包，两个接受规则独立 | 共享底层值得，完整出题系统不必上线；不能把“这个输入能反驳 H”当“该题教学合格” |
| **①＋⑦** | 部 | 修复前后同一用例与回归集合提供诊断支持／反证；可检验补丁是否过度修改 | 共享源代码哈希、父子版本、测试版本；⑦判断修改行为，不推断人的能力 | 对开发者工具有价值；在学习主线自动修复会干扰③，应由用户手写或只审查已提交版本 |
| **②＋③** | 高 | 训练后用未暴露题检查，而不是重复原题并统计 AC；失败能调整后续训练 | 同概念但不同题族／暴露状态，训练集与验收集隔离，提示事件、首尝试记录共享 | A 必需的逻辑连接；维护等难度、等目标的新题是主要成本。仅换变量名的新题不证明迁移 |
| ②＋④ | 部 | 训练阶段有脚手架与逐步提示，可以降低卡住成本 | 共享训练任务、当前步骤和提示历史；有提示结果标 assisted | 可选；固定提示和教师答疑更简单。若提示直接代写，训练完成不能作为独立验收 |
| ②＋⑤ | 低 | 只有把训练目标限定 SQL 概念才增加价值 | 需要 SQL 误解分类、诊断问和迁移题；通用学习者身份仅是浅共享 | 当前不值得；多语言覆盖不是必要协同 |
| **②＋⑥** | 高；局部重 | 训练题经过目标错误检测，不只在题面写“考查循环”；不足题量时可提供合格变式 | 共享目标概念／误解、难度与题包版本；②负责选题，⑥负责候选审核；不要各建一个概念映射器 | 题量确实不足时值得；已有足量人工合格题时⑥是可删除后台，②不依赖自由生成 |
| ②＋⑦ | 禁 | 自动修复可能帮助完成任务，但没有训练迁移收益保证 | 补丁属于辅助事件，不能充当迁移作答 | 当前反作用大；若另设“读补丁解释”课程，应另定义学习目标，不能悄悄接入本主线 |
| ③＋④ | 部；需隔离 | 提示暴露记录使独立资格可核查；失败后可以转回训练 | 验收期间关闭题目相关 AI 输出；一旦请求提示，当前观测转 assisted，不能重置计数重新冒充独立首测 | 值得共享审计，不能在独立验收时同时启用提示。关闭应用内 AI 不能证明未使用外部工具 |
| ③＋⑤ | 低 | SQL 学习者也可做独立新题检查 | 需新建概念题库和 SQL 专用预言机，③的事件资格规则可沿用 | 协议可复用，当前无必要扩场景 |
| ③＋⑥ | 部 | 若验收题自动生成，质检与未暴露题族检查可避免失效观测 | ③消费已审核题包 ID，不能消费⑥尚在修复的草稿；验收题不能进入学生／模型可见训练上下文 | 保留题包检查接口值得；固定盲验题足够时无需在线生成。此关系不同于②⑥持续补训练题 |
| ③＋⑦ | 禁 | 补丁通过能确认代码修复，但会破坏独立编写证据 | 保留 patch provenance；③拒绝 AI 写入或展示目标题答案的事件 | 不合并同一次验收。工程验收与人的能力验收是两个对象 |
| ④＋⑤ | 低 | SQL 可使用提示阶梯 | 需要方言专用提示策略、查询结果与 schema 上下文；没有自然共享的核心判定 | 当前不值得；以后装配在 SQL 插件中 |
| ④＋⑥ | 部 | 审题时检查候选提示是否越级，生成可审阅提示卡 | 题包携带解法与允许提示信息，学习端只收到获准部分；质检和泄露审核分开 | 可选；简单题可由教师写提示，不需要双模型自由生成与自审 |
| ④＋⑦ | 禁 | 修改建议通常比“提示”更直接，但会改变产品行为 | 生成补丁与低泄露提示用不同模式、不同日志；不得把展示精确修改计为未泄题 | 当前不值得。若用户主动选修复模式，应明确改为辅助完成，不计③ |
| ⑤＋⑥ | 低 | SQL 题生成可以使用数据库反例检测 | 必须另做合法 schema／数据生成、查询期望、方言与目标变异体；只有通用任务协议能共享 | 不把 Python 题工厂扩大成 SQL 题工厂；先有目标用户再扩 |
| ⑤＋⑦ | 部 | SQL 查询修复前后可在多组夹具上比对 | SQL adapter 输出结果语义；补丁 adapter 保存版本差异；有限数据库测试不证明查询普遍等价 | 有 SQL 维护需求时值得；当前作为专业插件方向 |
| ⑥＋⑦ | 部；局部重 | 两者都需要冻结可信预言机和测试版本、检测弱测试、比较程序版本 | 共享执行器与变异体工具；⑥检查题包，⑦检查候选补丁。生成器不得修改验收测试使候选通过 | 技术复用值得；面向教师与开发者的两个产品流程不用强行合并 |

## 3. 必须统一的逻辑与必须独立的模块

### 必须共享的契约

| 共享能力 | 使用者 | 为什么必须统一 | 为什么不必同进程或同数据库 |
|---|---|---|---|
| `ProblemSpec` 与版本哈希 | ①②③⑥；⑤⑦经适配 | 题意、输入前提、参考来源、测试版本变化会使旧结论失效 | 导出题包和事件可通过 ID／hash 连接 |
| `ExecutionEvidence` | ①③⑥⑦；⑤用专用 adapter | 不同模块不能各自生成相互矛盾的“实际输出”；记录超时／截断／环境失败 | 统一 JSON 契约，runner 可更换；不要求同一种执行引擎 |
| 概念与误解词表 | ①②③⑥ | 诊断与选题若使用不一致标签，无法追踪错误训练 | 一个版本化词表即可，不需要图数据库 |
| 暴露／辅助事件 | ②③④⑦ | 同一题看过答案、提示或补丁会改变独立资格 | 应用以事件记录关联，资格判定由③负责 |
| 诊断与观测的状态引用 | ①②③ | 待定诊断不能偷偷转成 confirmed；错误确认可撤回关联推荐 | 追加更正事件而非覆盖所有历史 |

### 必须保留的模块边界

运行器只生产执行事实；诊断器只提出／核验有限程序假设；学习者误解确认处理追问与行为证据；训练选择器消费已确认目标；掌握检查器决定观测资格；题目质检器审核候选题包；调度器只决定何时复习。**上述分工是设计建议，尚未实现。**

①②③需要共同的数据链和状态规则，构成 A 的核心机制；它们不应合成一个让 LLM 任意读写所有状态的 Agent。④是独立提示策略，⑥是离线／后台题包能力，⑤是语言插件，⑦是另一个修复工作流。B 是①的受限核验引擎加④的交互策略，不再另复制一套“可信诊断页面”。

## 4. 删除功能后损失与更简单替代

以下“高／中／低”是目标相对价值判断，非用户试验量化结论。

| 删除对象 | 对 A 的损失 | 对 B／C 的损失 | 更简单替代或处理 |
|---|---|---|---|
| ① 完整诊断 | 高：不能由错误可靠选训练；但仍能由用户指定概念做②③ | B 核心消失；C 只需执行，不需要完整学习者诊断 | 人工选概念＋固定诊断问，可作为强对照 |
| ② 迁移训练 | 高：退化为诊断与考试，无法补知识 | B 低；C 需要目标输入，未必需要训练编排 | 有限人工题映射即可，无需自适应推荐模型 |
| ③ 独立检查 | 高：只能声称帮助改题，不能声称学习状态有独立依据 | B 低；C 低 | 固定、未暴露、同概念新题和事件规则即可，无需 BKT 训练 |
| ④ 动态分层提示 | 中低：可先给固定确认问或基础反馈 | B 中：解释与追问可保留，动态提示可删；C 低 | 教师审定提示卡；③仍须记录所有辅助 |
| ⑤ SQL | 对当前 Python 用户低 | 对当前 B／C 低 | 暂缓；协议预留 adapter，不建 SQL UI |
| ⑥ 在线题生成 | 有人工合格题时低；题供给不足时中高 | B 低；C 产品核心消失 | A 保留题包验证接口与有限参数变式，生成器可以不启用 |
| ⑦ 自动补丁验收流程 | 对学习主线低，减少辅助污染 | 通用开发者 B 中；教师 C 低 | 回放用户手写版本和固定测试足够 |
| FSRS／知识图谱／多 Agent | 首阶段低 | 均非核心必要 | 简单到期队列、版本化标签、单次结构化模型调用 |

## 5. 最小且有协同的组合

保留 **①＋②＋③**，用 B 提供有限诊断核验，②优先消费固定题包；④按需提供受限提示并记录暴露；⑥只做现有题包的基础与目标错误检查。将同一事实从失败提交传到确认、训练与独立观测，才是组合额外价值。是否值得扩大自动生成、SQL 或自动修复，必须由新增用户需求和独立实验支持，不能由“已有共同运行器”推出。
