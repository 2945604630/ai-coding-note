### 2.1 本轮核对发现的关键断点

**Docker 可运行新源码，但新结果尚未形成统一的教学上下文。** 静态查看 [service.py](<../../../web_lab/service.py>) 的 `new_turn`，它查询 `demo_operations` 后调用 `make_public`；[teaching.py](<../../../web_lab/teaching.py>) 只将旧 F03/F04 核验结果投影进教学证据。新执行保存在 `sandbox_jobs`，本轮未见它被上述入口纳入 AI 请求。

新源码还会进入“未审核代码记录”，其警告将其描述为没有可信执行证据。这个旧标签需要与“已有 Docker 实际执行，但尚未纳入教学核验”区分。**这是代码检查所得的集成缺口，不是本轮线上试验结果。** 不能宣称现有 AI 已针对学生最新 Docker 结果完成端到端辅导。

其他短板：

- [旧 V2 限制](<../old-ui/v2/V2_limitations.md>) 中“任意新代码不能运行”已被 P1 在 SUM 合同内更新；旧 F03/F04/F05 白名单仍保持，MAX 新题自由源码没有因此自动获准执行。
- 当前普通学习入口只有 C01/C03 两个 SUM 场景；现有提交仅比较 0、1、3，且没有真正隐藏测试。不能包装成广泛 Python 课程或强正确性验收。
- V2 检查记录明确 `real_user_trial_completed=false`、`teaching_accuracy_certified=false`。自动化来源更正事件已保留，不能把页面创建标签当成真人人数。
- 本次本地搜索未检出项目自身 LICENSE/NOTICE，也未核对已发布且持续可访问的成果链接。现有依赖、模型服务与团队代码需要分别整理；“代码放在本地”不等于已形成合格开放成果。

### 2.2 组合价值与创新证明的界线

[综合集成结果](<../feature-validation/F01_F05_integration/F01_F05_integration_results.md>) 是两场景历史回答回放，含 21 次真实受控执行与版本关联；不是实时真人学习闭环。[产品评估](<../feature-validation/F01_F05_integration/F01_F05_product_assessment.md>) 已说明：防混淆的记录规则有工程价值，没有真实用户优势比较，五模块相加不能证明创新。

我们已有的是：**一套可演示的有限应用骨架，以及相对扎实的记录和执行边界。** 尚无证据的是：真实需求收益、完整实时辅导、独立教学机制、有效迁移测量和比赛所需的公开/受限成果包。

## 4. 三条最终路线的直接比较

成本为本报告工程估算，不是官方要求或实测工时：假设一名熟悉当前 Python 项目的开发者、Coding Agent 辅助、每人日约 6 小时有效工作、现有 Docker 可用、仅本机单人演示；包含小量人工检查、成果整理和视频，不包括公网服务。实际可投入时间和 API 预算未知。

| 决策问题 | A：现有 AI 编程练习台 | B：明确合同下的 AI 补丁验收 | C：OpenHands 教程验真 Agent |
|---|---|---|---|
| 官方主题 | 对应 AI 应用创新；教育场景清楚 | 对应 AI 开发工具；测试与代码修改清楚 | 对应开源项目改进；以教程/文档工具作贡献 |
| AI 核心作用 | 理解自由回应并生成针对当前代码/证据的解释 | 理解 Bug/代码，提出补丁和解释实际剩余问题 | 将自然语言教程关联源码、环境与步骤；诊断失败并提出文档补丁 |
| 非 AI 核心 | 执行、版本关联、帮助与学习记录 | 固定规范测试、前后对照、失败/未知和导出 | 步骤覆盖、受限执行、环境/版本绑定及结果矩阵 |
| 先行重合 | 高：SmartCode、Iris、CodeHelp 等已有类似辅导与运行 | 高：常规测试/差分、CoverUp、SWT-Bench 与 coding Agent | 高：OpenHands 已能读文件、用工具、改文档，普通任务提示可能同效 |
| 几分钟能展示 | 一次回答、真实改码/运行、同版本证据和停止选择 | 一个“局部测试通过但仍错”的补丁被固定规范测试拒绝 | 逐步教程中未执行/失败被定位，最小文档修正后复验 |
| 最少剩余工作 | API 实联/等待体验、新执行→AI 上下文、真实试用、开放/提交材料 | 独立补丁入口、审查 AI、固定规范与新合同、开发者反馈、开放/提交材料 | 新底座接通、自定义工具、全步骤审计、新运行权限、维护者材料、开放/提交 |
| 到有限可提交作品的成本 | **7～10 人日**，维持当前 SUM 范围；新增第二输入合同另加约 3～5 人日 | **9～13 人日**，只做固定业务族的 Bug 修复 | **12～18 人日**，只支持一个教程类型；换平台返工风险更大 |
| 与已有工程兼容性 | 最高；保留主体 | 中高；复用证据与部分 UI，教学/F05 不是主体 | 低到中；复用事件/证据设计，不能直接搬 SUM 沙箱 |
| 最大短板 | 用户价值与教学质量未证、范围窄、实时上下文和延迟 | 看起来容易成为普通 AI＋测试面板；AI 审查尚未实现 | 所谓增量尚未实测，部署/权限/教程真值又引入新工作 |

| 当前投资结论 | **第一选择，CONDITIONAL GO：应用收尾** | **备选，CONDITIONAL GO：用户决定转向后再做** | **本届默认 NO-GO，不启动替换** |

B/C 的演示是计划，不是本轮已完成能力。上述“对应主题”是对已查规则的适配判断；并非组委会预审通过。现有项目能够承受的开发投入没有因截止延期自动增加。

## 5. 方案 A：收尾一个有限的 AI 编程练习应用

**建议作品名：证据可追溯 AI 编程练习台。** 用户是正在练习 Python 循环/调试的初学者；核心任务是自己解释、修改、运行，并看清 AI 建议和当前代码实际表现的关系。最小提交范围维持 SUM 合同，明确披露两场景，不自称完整课程、有效迁移测验或长期学习平台。

### 5.1 为什么值得优先

界面、存储、对话与执行的主要工程已存在。F01 的真实输出说明模型能够接续否定、比喻、非标准表达等自由回应；这属于通用 AI 能力，但在应用中确实有工作可做。执行和记录由程序负责，不再用 AI 判断精确数值或“是否掌握”。

相比普通聊天＋手工运行，已有自主工作是保存回答、代码版本和对应证据，防止旧结果冒用于新版本，保留局部失败与未知。**这些是现有工程能力，不是新发明，也没有得到相对 SmartCode/Iris 的独占性证明。** 最值得补的差异是把它们做成一个学生实际可用、结果不混淆的完整流程，并用用户记录证明它值得使用。

核心开源/开放关系不能只列 FastAPI、Uvicorn 等开发依赖。Python 运行环境与隔离执行应在作品中承担真实核心任务；团队的版本—执行—记录接口、受限运行策略及可复核案例应形成可复用成果。模型/CLI/API 按实际第三方工具或服务披露，**未取得模型开源权重证据，不把其写成“开源大模型”**。这一安排是主题适配方案，不等于融合深度已经获得官方认可。

### 5.2 几分钟演示的具体流程

1. 打开已有练习，先实际运行当前版本，再让学生解释为什么 `range(n)` 的求和结果与题意不同；模型根据原话和本次版本绑定的证据回应。
2. 学生保存修改，点击真实运行/提交；展示相应版本的输入 3、实际返回、参考与状态。
3. 换到错误或局部修复版本，显示此前成功不适用于当前版本；学生继续自行改或停止。
4. 查看简洁历史：自己的回答、帮助、修改和真实结果保留；不输出“已掌握”。

只需一个核心例子，不依靠新探针、迁移选题或多个 Agent。当前新 Docker 结果→AI 的断点须先补齐，演示才能声称针对最新代码。若使用真实历史录屏压缩等待，明确标记原耗时；不能用回放伪装实时回复。现场流程控制在 3～5 分钟是作品设计目标，不是当前实测成绩。

### 5.3 收尾工作与预算边界

| 工作 | 估计 | 完成依据 |
|---|---:|---|
| 选定一个真实 Provider 并改善等待体验 | 1～2 人日 | 实际请求成功/失败有记录；不把替身测试当 API 联通；收费与延迟如实保存 |
| 新执行证据接入当前 AI 上下文 | 2～3 人日 | 来源、版本/哈希、输入与实际结果绑定；旧证据不冒用；异常/超时不填成功 |
| 有限真人使用与教学措辞复核 | 1～2 人日 | 建议 2～3 人各完成一次短练习，记录卡点/反馈；这不是学习效果实验 |
| 运行说明、许可/自研边界、成果链接、报告和视频 | 2～3 人日 | 在干净环境有明确复现步骤，实际完成内容可核验 |

合计约 7～10 人日是规划区间，工作可能重叠；不用表格相加假装精确排期。外部模型费用取决于用户选的服务、调用量与额度，本轮不估算现金金额。建议留最后至少 3 个自然日用于材料、权限核对和提交，不继续扩玩法。

第二输入合同/更丰富课程不包含在这个最低预算里。若只有两场景不足以支撑预期作品定位，应主动降低范围表述；不要临时生成题目再称有效题库。

**准入底线：** 一次真人可完成核心流程，AI 能获得准确的当前材料，运行/失败记录可信，能说明至少一项实际自主改进和它的使用价值。若最终仍只有聊天、运行按钮和 UI 调整，应用创新证据仍不足，不能因为“没要求新算法”就宣布充分完成。

## 6. 方案 B：明确合同下的 AI 补丁验收与回归证据助手

**这是备选的工具作品，范围为 Bug 修复，不覆盖自由业务需求变更。** 用户提供题意/已确认规范、代码与失败现象；AI 解释可能问题、提出可编辑补丁；用户选择是否接受；执行器运行固定规范测试，对照前后版本并导出仍失败/改善/回归的证据。

预期值来自事先审定的合同或独立参考，不能来自 AI 新补丁输出。未知规范、超时、未执行项都单列。**不建立 R1 意图选择层，不开发 R2 测试预期来源审查。**

### 6.1 已有基础与 AI 作用

F04 的 M02 已有真实输出：局部补丁在 n=1 通过，但 n=0 仍失败、n=3 返回 8 而参考为 6。M03 已有原通过→新失败。这给 B 一个清楚的产品示例；来源是作者安排的受控任务，不是真实开发者 PR。

AI 真正承担开放 Bug 描述/代码理解、补丁建议及解释；固定测试与结论不需要 AI。当前 F04 的反馈是确定性模板，不应说成 B 的新审查模型已经实现。Provider 传输可借用，审查输入、提示、响应与输出核验需要另做。

[已有先行技术调查](<../p2/P2_project_reselection.md>) 已确认 CrossHair 差分、Hypothesis 搜索、CoverUp 测试生成、SWT-Bench 前后状态评价及需求判定研究。故 B 的主张只能是一个面向小程序的、接受 AI 修改前便于使用的验证流程；不能称“首次 AI＋测试”，也不能认领 R1 的失败假设。

### 6.2 现场展示与剩余工作

三步演示：展示 M02 的“局部通过”；展示其他规范输入仍错；换完整修复补丁，显示改善并保留原结果。AI 给出针对实际结果的解释，测试工具决定有限合同成绩。已具备前后对照底层数据；独立工具入口、新 AI 审查和 Docker 合同内的端到端链尚未完成。

最小工作约 9～13 人日：固定业务族/规范与运行合同 2～3，AI 审查和版本任务编排 2～3，简洁工具入口与导出 2～3，API/开发者使用检查及提交材料 3～4。新的合同是独立受限工程工作，**既有 SUM 沙箱不会因改作品名称而自动支持字符串、pytest 或仓库命令**。

只有 SUM 演示时，B 的价值与 A 都很窄；若要做真正的小业务工具，需要至少一个非玩具的已审定示例及其合法隔离合同。不能拿 R1 的人工推演作为真实 Docker 成绩。

**最大短板是重合和 AI 薄。** 评委可以合理问“这不就是让 AI 修代码再跑测试？”答案应承认其普通工具属性，只凭实际使用、准确的验收边界和清楚的自主工作说明应用改进。若只有测试表和模板解释，不构成强 AI 作品。

**什么时候选 B：** 用户更愿意服务代码修改验收，能取得明确规范与开发者使用材料，且接受重新做工具入口。找不到学习者时 B 较容易以程序结果验证核心功能，但仍不能跳过需求价值和 AI 作用说明。A 的 API/延迟问题也会影响 B，换方向不会自动消除它们。

| 判断 | A | B | C |

## 9. 最终选择与止损边界

**选 A：补齐已有应用的实际断点，准备一个诚实的有限作品。** 优先级是：
1. 当前源码/执行结果进入同版本的 AI 上下文；实际 Provider 与失败/等待体验可用。
2. 一次真实使用能完成核心练习；反馈如实记为可用性与感受，不升格为教学效果。
3. 开放/受限成果访问方式、资源清单、自研边界、复现说明和 3～5 分钟视频齐备。

A 的最弱项仍是创新与价值证据。若用户目标是“必须获得明确独立技术突破”，当前 A 不满足；本届时间内换普通 Agent 也没有证据能解决。若目标是提交一个真实完成的 AI+开源应用，A 是当前风险最低的选择。

**备选 B：用户明确愿意换成代码修改验收工具时再启动。** 它可以减少对教学真值/题库的依赖，但需新的应用入口、AI 审查和适用合同；不是给现有页面换标题，也不是继续扩样 R1。

**不选 C 作为救场。** 成熟 Agent 只省通用执行与会话基础，不提供我们的需求、合法材料、专用效果证据或参赛差异。12～18 人日的预计工作接近全部剩余窗口，不能因已有项目没有创新证据而默认换一个。

本轮不生成申请/参赛材料、不发布代码、不修改现有功能；不开展 R2、新的教学机制或模型对照。用户选择 A 或 B 后，下一阶段应是限定作品的收尾与验收，而不是恢复循环式创新海选。
