# 技术复用与三条开发路线

核验日期：2026-10-08（Asia/Shanghai）。本文件只提出研究后的路线和验收顺序，未执行开发、Fork、依赖安装或发布。项目和版本证据见 [候选池](<open_source_candidate_pool.md>)，已实现能力见 [CodeHelper 分析](<codehelper_deep_analysis.md>)。

## 1. 当前建议

**下一轮先进行有限原型验证，再在“保留 CodeHelper”与“独立小应用”之间选择。** 原型验证不是先大改一个平台：先检验目标 Windows 的运行成本、核心诊断是否有可测收益、数据协议能否独立保存。不要同时接入所有候选。

若定位是 Python 小题学习，独立项目＋Pyodide＋小型测试集通常依赖更少；若需要 C/C++、本地文件与桌面分发，CodeHelper 的现成基础价值更大。ts-fsrs 是可选排程模块，首版诊断是否有效与换不换 SM-2 无必然关系。

## 2. 路线 A：直接 Fork CodeHelper

### 适用条件

已有 Windows 工具链能跑通固定提交，需求需要编辑、判题、错题、复习和桌面数据保存，核心改进能集中在一个入口与少量新表。它在候选中最接近完整桌面底座。SmartCode 可作为 Python-only 的备选，但 MySQL、题目执行配置和薄弱测试使其没有明显确定优势。

| 动作 | 建议范围 | 自主开发边界 |
|---|---|---|
| 保留 | Electron、CodeMirror、preload 边界、AI Provider、SQLite 迁移／备份、提交与错题路径 | 这些归上游，保留许可和版本说明 |
| 首版保留基线 | SM-2、可信本机运行器、提交历史 | 用来对照，不宣称原创 |
| 首版隐藏 | 课程、成就、宠物、通用工作区的非必要入口、复杂知识维护 | 隐藏不解除依赖，不夸大精简量 |
| 后续删除 | 不使用的页面、IPC、资源、状态、依赖 | 先追踪调用与迁移，再删；不要首次启动前批量删表 |
| 新增 | 执行证据保存、结构化诊断假设、针对性追问、独立验证题与效果统计 | 自主成果重点，必须有测试和提交证据 |
| 替换内容 | 小型自拟题或核验许可的题集 | 不直接继承全量外部题面 |

最小新增数据可包含 `attempt_evidence`、`diagnosis_hypothesis`、`probe_answer`、`transfer_result`；这是拟议的数据边界，不是已经创建的表。原 `mistakes` 存最后错误代码和文本分析，无法单独容纳所有验证事件。[原 schema](https://github.com/SuLiverse/CodeHelper-Studio/blob/23773e843d2a7bc3b04eedff59055b6c3a7afe7b/electron/db/schema.sql)

**实施顺序（后续开发阶段）：** 固定上游提交与许可→运行原始基线→增加证据协议和新表→接一个诊断入口→用原 quickAsk 对照→加一类独立新题→再隐藏非核心入口→补安装和材料。预计 2～4 周形成较完整专项作品；若仅新增一类证据诊断且环境顺利，可能压缩到一周，但未运行前不能承诺。

主要风险是原生 ABI、runner 的平台依赖、草稿／工作区恢复耦合、资源权利和演示稳定性。保留 runner 要保留进程监督，不得为了精简删除保护再宣称等效。保留 AI Provider 应继续在主进程管理 Key。[runner](https://github.com/SuLiverse/CodeHelper-Studio/blob/23773e843d2a7bc3b04eedff59055b6c3a7afe7b/electron/utils/codeRunner.ts)、[API Key](https://github.com/SuLiverse/CodeHelper-Studio/blob/23773e843d2a7bc3b04eedff59055b6c3a7afe7b/electron/utils/apiKeyStorage.ts)

## 3. 路线 B：独立应用＋成熟模块

### 最小组合 B1：Python 反例／诊断应用

| 部分 | 方案 | 复用与自主内容 |
|---|---|---|
| 前端 | 自己的 React／TypeScript＋轻编辑器 | 只做题目、运行证据、诊断、验证四个区域；参考 CodeHelper 的服务边界，不搬全部 UI |
| Python 执行 | Pyodide 官方发布包＋module Worker | 复用运行时；自己实现输入协议、输出捕获、用例结果、取消／超时和状态清理 |
| 数据 | 浏览器 IndexedDB；若需要桌面再 Electron＋SQLite | 单用户原型可先少量事件；正式方案要导出与备份。不要无边界保存 API Key 到浏览器持久化 |
| AI | 单一 Provider 的本地 Node 代理，或 Electron 主进程 | 自己定义诊断输入／输出、证据校验、失败状态和调用上限 |
| 练习 | 自拟 10～20 小题，或少量核验后的 Exercism Python | 改编题需标明来源和修改；明确函数式／stdin 模式转换 |
| 排程 | 可选 ts-fsrs scheduler | 复用算法；自行定义什么事件算独立正确、如何记录提示依赖 |
| 学习机制 | 参考 SmartCode 的运行事实覆盖、OpenTutor 的追问／概念状态、Iris 的提示合约 | 对具体协议进行专项设计；不同时引入三个 Python 后端 |

自己实现题目列表、提交事件、几个概念标签和单用户错题记录，通常比迁移平台权限、课程管理、资源包、全局画像更简单。需要防止“独立项目”变成再造完整 OJ。

技术主线为：题目＋代码→确定性执行→保存证据→AI 提出一个或两个可检验假设→用户回答一问或做一题→更新学习状态。**代码通过用例只是程序行为证据，不足以确认学习者理解。** AI 负责选择追问和解释，程序负责判定事实，二者分工是自主设计的一部分。

### 组合 B2：低部署教学审计工具

若受时限限制，可以以已有提交证据文件为输入，参考 Iris／TuTor 的“给一步提示、验证一步”，构建小工具生成不泄题的提示并保存证据。首次 Demo 不必有完整在线编辑器，但至少应展示真实输入、模型输出、自动检查、人工审阅和结果导出。只导入截图然后生成漂亮分析不足以证明核心改进。

### 不建议的组合

- Electron＋Next.js 全站＋FastAPI＋MySQL＋Redis＋Weaviate＋Judge0：把每个候选的部署成本都叠加，独立模块没有形成成本优势。
- 同时运行 Judge0 和 Piston：二者先作为替代方案，不是互补需求。
- 直接复制 OpenTutor 的完整 Agent 路由和 Iris pipeline：协议、DB、课程、回调和 Python 版本都不同。
- 把 pyKT 模型嵌进新项目并马上训练：本场景缺带概念标签的交互数据；首轮不依赖训练。

## 4. 路线 C：快速原型后决定保留或重建

### 如何减少原型工作量

后续开发授权后，借 CodeHelper 的编辑／提交／错题界面，只加一个诊断实验入口；或借已有合规 Dify 实例编排 AI 输入输出。无已有 Dify 环境时，不为几次调用部署整套服务。原型只解决一个语言、一个错误族、一个新题验证，不做账号、课程图谱或复杂仪表盘。

### 如何避免推倒重来

先固定平台无关的记录：

| 记录 | 最少保存内容 | 迁移价值 |
|---|---|---|
| ProblemSpec | 自主 ID、题面、概念标签、函数／输入协议、参考实现来源、测试集版本 | 不绑原平台整数 ID；内容和版本可重用 |
| AttemptEvidence | 代码哈希、运行时版本、用例 ID、输入、期望／实际输出、stderr、状态、提示使用 | 提供事实和回放基础；注意输出截断 |
| Diagnosis | 候选错因、证据 ID、追问、模型／prompt 版本、核验结果、是否证据不足 | 能比较模型与真实标注，不只保留一段总结 |
| LearningObservation | 原题／新题、独立／辅助、正确性、提示次数、时间、人工确认 | 支持“会做”和“靠提示做”分开统计 |
| ReviewEvent | 时间、rating、来源、算法版本和关联 attempt | 不强行把 SM-2 参数无损映射成 FSRS 状态 |

使用 JSON／JSONL 导出这些记录并保存一小套固定案例。UI、runner 和数据库通过适配层连接。**原型产物首先是协议、案例和评测，平台是否保留其次。** 本轮只建议这些接口，没有生成实现代码。

### 决策门槛

| 观察结果 | 后续选择 |
|---|---|
| 1～2 天内目标系统基线可运行；新功能仅影响少量路径；备份和已有流程正常 | 保留 CodeHelper，继续专项化 |
| 两天仍被 native／打包／工具链阻挡；改一个实验必须改多套状态和 IPC | 停止扩大平台改造，转 B1 独立应用 |
| 新机制与原 quickAsk 相比没有更准确／可核验的输出 | 缩小机制或换机会；不能靠换架构掩盖无收益 |
| 只能跑静态样例，无法让正确／错误程序形成真实结果 | 先解决执行与回放，不做更多页面 |
| 生成题经常不成立或测试无法判定 | 收回到固定题模板＋参数变式，保留 AI 解释或选择能力 |

上述是预设止损条件，未执行计时实验。不会为了维护原型投入而默认保留原平台。

## 5. 技术兼容性与组合边界

| 组合 | 可行方式 | 必须处理 |
|---|---|---|
| CodeHelper＋ts-fsrs | 两者都是 TS 生态；新建 scheduler adapter | SM-2 的 quality 0～5 与 FSRS 的 rating 1～4 不可机械照搬；保存日志并指定迁移策略 |
| 独立 React＋Pyodide | module Worker＋消息协议 | 函数式／stdin 模式、stdout、异步执行、超时后重建 Worker、持久化变量污染、缓存和离线资产 |
| CodeHelper＋Pyodide | renderer Worker 使用运行时；保持 Electron nodeIntegration／桥接边界 | 若只需要 Python，可替代一条执行路径；双运行时可能增加行为差异，首版不默认同时保留 |
| JS 应用＋OpenTutor BKT | 将相对独立公式按许可迁移为 TS，或单独小接口 | BKT 先验／guess／slip 适配编程题；核验现有公式、不能声称自主算法 |
| JS 应用＋Iris 提示机制 | 参考或迁移指定 MIT 模板／协议 | 保留署名、解除 Artemis DTO／回调依赖；不复用全部 Python 服务 |
| Exercism＋执行器 | 只取少数题，改成明确函数 API 或受控测试 harness | pytest／unittest 依赖、模块导入、测试重置和测试可见性；Pyodide 能跑 Python不代表原题能直接判 |
| 应用＋Judge0／Piston | 独立 HTTP 服务，分别维护版本和许可 | Linux 沙箱、Docker／WSL2、镜像、资源与网络；GPL 是否涉及衍生作品要按组合实际关系判断 |

Pyodide stable 文档和最新源树并不保证与旧 0.27.x 资产兼容；实现时应固定一条版本线和相应文档，不使用浮动 CDN `latest`。当前优先消费已核验的稳定 Release 314.0.7，不从源码重建。[稳定发布](https://github.com/pyodide/pyodide/releases/tag/314.0.7)、[Worker 说明](https://pyodide.org/en/stable/usage/webworker.html)

OpenTutor 的进程 runner 含 `resource`／`signal.alarm`，Windows 原生不可原样迁移；代码执行模块还会选择容器，不能把其“本地 SQLite”描述成“所有模块 Windows 无依赖”。[执行后端选择](https://github.com/zijinz456/OpenTutor/blob/5fea390a49be81827342caa19846fecbcf147e4a/apps/api/services/agent/code_execution.py)、[进程 runner](https://github.com/zijinz456/OpenTutor/blob/5fea390a49be81827342caa19846fecbcf147e4a/apps/api/services/agent/sandbox_runner.py)

## 6. 许可组合检查

| 资源 | 已核验许可 | 实际复用方式与义务 |
|---|---|---|
| CodeHelper、SmartCode、OpenTutor、EduTelligence、ts-fsrs、Exercism Python、Piston、TuTor、CF Compass | MIT | 可改适用代码；保留原版权和许可，第三方清单列版本、文件和修改；不把上游作为自主作品 |
| Pyodide | MPL-2.0 | 作为独立运行时使用可与独立 MIT 文件组合；分发受覆盖文件和修改时提供相应源码取得方式和许可通知，运行时依赖另查 |
| Judge0 | GPL-3.0 | 修改／衍生软件分发需按 GPL 提供对应源码和通知；不要直接抽到 MIT 项目后删许可。单独服务不是自动免除所有义务的证明 |
| Dify | 附加条件 Apache 改版；API NOASSERTION | 多租户和前端 LOGO／版权修改有额外条件；不选为自由改名分发的底座 |
| 各题库、论文、公开数据、平台题面、图片 | 逐项核查 | 网页公开可访问、根 LICENSE 或参考论文不自动等于可训练／改编／再分发授权 |
| LLM／Coding Agent／模型权重 | 按所用产品版本和条款 | 披露辅助开发与审核；开源运行时不等于模型开源，也不要求强行自部署昂贵模型 |

MPL 文件边界参考 [Mozilla 官方 FAQ](https://www.mozilla.org/en-US/MPL/2.0/FAQ/)；GPL 依据本轮实际读取的 [Judge0 LICENSE](https://github.com/judge0/judge0/blob/491be91bdd2c5c699d47adc3c9e48019d3074229/LICENSE)；Dify 条件依据 [固定 LICENSE](https://github.com/langgenius/dify/blob/c21f5ce070652932b158afd934abbb181ef3040e/LICENSE)。这是针对所述组合的工程筛查，尚未完成全依赖及资产审计。

具体可行组合是 **独立应用＋MIT 代码模块＋独立 MPL 运行时**，分别保留许可与原始源码／版本信息。不能将整个组合统称“全部 MIT”。如果最后只参考机制而未复制表达或实现，也应在报告中注明参考来源和本人的实际设计。

## 7. 现实时间与成本

### 2～4 周开发窗口

| 阶段 | 主要成果 | 可检验退出条件 |
|---|---|---|
| 第 1 周 | 单语言执行、固定题集、证据保存、原始 LLM 基线 | 正确／错误／超时案例能回放，模型失败被明确记录 |
| 第 2 周 | 一个自主机制、人工标注、对照评测 | 新机制至少在预设指标上得到可解释结果，包含失败案例 |
| 第 3 周（若有） | 新题验收、用户小规模试用、数据恢复 | 辅助与独立事件分开，报告不能从少数用户泛化 |
| 第 4 周（若有） | 稳定、演示、报告、许可清单和开放成果 | 干净目标环境复现；演示与提交版本一致 |

### 本届初赛只有约一周

[官方通知](https://www.aicomp.cn/tracks/tracks-5/4924.html)规定 10 月 15 日 20:00 提交且截止后无法修改。若继续参加本届，后续开发必须再缩范围：10 月 8～9 日确认基线与一个机制，10～11 日完成小型真实流程，12 日完成对照案例，13～14 日稳定与录制，15 日留提交余量。**这是条件性安排，不是保证当前空项目一周能获奖。** 四周方案只能用于更长开发窗口或按后续明确通知允许的阶段，不把复赛当作当然补开发时间。

不列未经核验的 API 单价。估算方式为：总费用＝各 Provider 的输入 token ×实际输入单价＋输出 token ×实际输出单价＋其他收费。每次失败提交首版最多一个诊断调用，只有需要时再一个追问／选题调用；先用固定题减少生成与多 Agent 自审成本，缓存固定材料。

例如 50 个案例的基线和新方案各一次调用，共 100 次；若每次 2,000 输入＋600 输出 token，则约 200,000 输入＋60,000 输出 token，再加重复试验和重试。这个是用量假设，不是账单或效果结果。没有 GPU 条件时，不把“本地 Ollama 免费”当作低成本承诺。

## 8. 面向 AIC 的成果归属与验收

官方六项权重与用户给定一致，最重为实现与可验证效果 25 分。本路线应形成：清楚的小场景；一个自主机制；AI 与开源运行／排程／测试的实质连接；可重复的基线与新方案数据；可授权的案例和评测工具；准确材料。普通 API 调用、换主题和拼模块都不单独证明创新。

拟提交开放成果应集中在自主协议、去标识案例、验证题模板、测试记录和评测工具；不要求向上游发 PR 才能体现开源价值。保留“资源名称／版本／许可证／使用位置／修改内容／权利边界”的清单，以及 Coding Agent 的用途与人工审核记录。[官方规则附件](https://www.aicomp.cn/wp-content/uploads/2026/08/%E9%99%84%E4%BB%B61_AIC%C2%B7AI%E5%BC%80%E6%BA%90%E7%AB%9E%E8%B5%9B%E8%A7%84%E5%88%99%E5%8F%8A%E4%BD%9C%E5%93%81%E6%8F%90%E4%BA%A4%E8%A6%81%E6%B1%820812.pdf)
