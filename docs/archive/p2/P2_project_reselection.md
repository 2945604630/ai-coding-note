# P2 项目重新选题：聚焦可验证的 AI 编程工具

调查日期：2026-10-11。范围：项目级筛选；本轮只交付本文，不开发原型、不修改 Demo、不调用教学模型、不开展机制实验。

**建议从通用 AI 编程学习台，转向“帮助开发者验证 AI 代码与测试”的小型工具。第一名：变更意图对齐的差分测试工作台；第二名：测试预期值来源审查器。两者均为 CONDITIONAL GO，仅值得用户选定后做一次小规模反证检查。** 没有候选获得“创新已成立”的 GO。第三名作为实用产品备选，第四名因直接先行实现淘汰。

这里的“竞争力”指问题清楚、技术差异可检验、现场能展示、失败后仍可能留下实用软件；不是获奖预测，也没有引用未经核实的官方评分标准。

## 1. 为什么换方向，以及现有能力能复用到哪里

[P2-A](<P2_A_next_decision.md>) 没有胜过优化 Prompt 与强问题树；[P2-B](<P2_B_next_decision.md>) 停在合格题对不足的材料门槛。二者不再优化。本轮不推荐追问、分级提示、普通执行反馈、探针分区、首次冻结、迁移选题、Agent 数量、知识图谱或学习画像。

## 3. 四个具体作品候选

以下示例均为**未来 Demo 操作设想**，本轮没有实现或实际运行。示例用于说清产品，不充当机制验证材料。

### R1 · 变更意图对齐的差分测试工作台

**排序第 1；CONDITIONAL GO。创新潜力中等，已有技术重合中高。**

**真实问题与场景。** 开发者接受 AI 补丁后，普通测试可能全通过，但补丁把需求以外的行为一起改了。反过来，直接要求新旧函数相等又会把合法需求变更判成回归。需要知道“哪些行为允许变化，哪些必须保留”。适合小型 Python 数据清洗、规则计算工具的代码审查；不做整仓自主修复 Agent。

**最终作品与操作流程。** 用户导入旧函数、候选补丁、旧合同与变更文字；点击“检查改动范围”；系统给出可编辑的“允许变化/必须保留/尚未说明”要求，用户确认后运行，展示需求条款与新旧行为相连的反例，并导出回归测试和审查记录。候选补丁可由任何 AI 或人工提供，工具不自动提交代码。

具体演示：旧函数区分大小写去重；新需求明确为“比较时忽略大小写，但保留首条原文、原顺序，且不修改输入列表”，范围限定短 ASCII 字符串列表。候选补丁把元素都转为小写再排序。输入 `["B","b","A"]` 下：
- 合法新行为应为 `["B","A"]`；
- 旧行为为 `["B","b","A"]`，这一差异是需求允许的；
- 候选补丁若输出 `["a","b"]`，则破坏保留原文和顺序，属于需求外变化。

这些结果是设想的已明确合同推导，不是本轮的执行成绩。换成正确补丁后，同一验证任务应撤销上述阻断，避免只挑错误补丁展示。

**AI 真正负责。** 把自由表述需求与相关代码联系起来，提出有原句出处的变化条件、保留性质与结构化测试草案；未知事项标出来。AI 不负责宣判执行事实，也不自动决定业务意图。没有 AI 时仍可由人写形式化条件；AI 的合理价值是减少这段语义转换劳动，必须测准确性与审核成本，而不是宣称数学上离不开 AI。

**其他模块负责。** 合同编辑与确认、结构化条件校验、输入边界、Hypothesis/可选 CrossHair 搜索、真实双版本执行、短反例、需求绑定与版本证据。对保留区可将旧行为作为相对参考，但必须标“兼容性”，不能假定旧实现正确；变化区使用确认的规则/人工参考，不能拿新补丁结果生成自己的正确答案。超时、未支持性质和没有反例分别记未知/未发现，不输出全域正确证明。

**与成熟工具相比拟新增什么。** CrossHair 找“行为不同”，本作品要在已确认意图下区分“允许不同”和“越界不同”，并让业务条款、输入区域与执行证据相连。CoverUp 以覆盖率引导测试，本作品以变更范围和保留要求组织验证。这是**系统机制＋可靠性验证工作流**，不是新的符号执行算法。

真正待证差异只有一个：在同样搜索预算下，能否少漏掉需求外回归、少误报合法改变，并减少人工形式化工作。如果普通 Prompt＋同一差分引擎已经一样好，新增层没有独立创新价值。仅附需求 ID、显示 diff、保存哈希属于普通工程。

**可复用/Fork 判断。** 首选本地版本/证据组件，使用 Hypothesis 库；CrossHair 作为可选分析引擎，不 Fork 全部学习平台。主体授权条件须保留，尤其 Hypothesis 的 MPL 文件与 CrossHair 的混合来源标注。初版只支持两个小业务族、确定性纯函数和已知可检查条件，不承诺任意 Python 项目。

**成本与最大风险。** 后续小筛查约 1～2 人日；完整比赛 Demo 约 10～15 人日。最大风险是意图到条件映射遗漏，导致错误的“允许变化区”替补丁开脱；另有用户确认负担、搜索支持范围和现场时延。这个领域已有需求判定研究，不能因界面漂亮就给高新颖性。

**最小反证实验（本轮不执行）。** 先审定 4 个变更任务，覆盖正确改动、两类需求外回归、需求未说明的边界；至少两个业务族。先冻结规范、旧/新代码、参考判定与失败标准，不让系统事后改业务规范。

强对照包括：①优化普通 LLM＋同一输入搜索/双版本执行工具；②人工写变化/保留条件＋同一引擎。相同原始需求、代码、可用事实和执行预算；候选与 LLM 基线各任务最多一次生成，不挑最好回复；人工基线单列形式化及审核时间。4 任务最多 8 次生成，开始可先用两项明显阻断任务，失败即停，不启动双 AI 判分。

指标是需求外回归检出、合法改动误报、条件翻译错误、未知是否保留、有效反例、人工修改数/分钟、执行数与等待时间；由冻结参考和真实执行核对，语义争议交开发者审核。**停止条件：**误把需求外改变批准；不能给出非重复的可执行差异；普通强基线同样正确而成本更低；或审核负担抵消语义转换收益。小样本仅决定是否继续，不证明整体提升。

**评委三问。**
- “早就做过？”承认差分测试与需求判定已有，只展示意图约束下的回归分类增量及其对照；尚无增量时明确说尚未成立。
- “接个模型？”展示模型提出的条件如何被编译/检查、如何约束真实执行，以及条件错误会怎样使机制失败；不是相信一段解释。
- “现场呢？”在同一输入上展示合法变化与越界变化，再换正确补丁复验；不以“所有 diff 都是 Bug”演示取巧。

### R2 · 测试预期值来源审查器

**排序第 2；CONDITIONAL GO。创新潜力中低至中等，重合风险高；比 R1 更依赖可审定的测试材料。**

**真实问题与场景。** 学生或开发者让 AI 为代码补测试，测试可能只是把当前错误结果写成 expected；覆盖率提高、变异分数不错仍不说明业务断言正确。适合验收 AI 生成测试、检查小项目 PR 中新加入的断言，最终作品是一个测试审查工具，不是自动出题或判学生掌握。

**最终作品与流程。** 用户导入函数、测试文件、说明文档和可用的独立参考；工具逐条展示断言依据，标为“实现快照/需求支持/来源未明”，运行对照后列出“测试遗漏”“预期值与明确需求冲突”“暂无法判定”，用户审核后导出修正测试建议。没有独立参考的断言保留未知，不发“已认证正确”徽章。

具体演示：接口要求排序并保留重复项，目标实现却用 `sorted(set(xs))`。新增测试把 `[2,2]` 的 expected 写成 `[2]`，在错误实现上全绿。工具先找到“保留重复项”的需求依据，再用受审定的 `[2,2] -> [2,2]` 对照，显示**错的是实现与测试共同采纳的规范**，不通过改 expected 让当前实现继续全绿。[Hypothesis 官方示例](https://github.com/HypothesisWorks/hypothesis)本来就用 `sorted(set(ls))` 展示重复项问题；我们的新增“错误测试”只是未来演示设想，不冒称刚发现的真实 Bug。

**AI 真正负责。** 理解文档中行为约束，追溯断言与其可能依据，提出需要核对的性质与测试修改草案。对动态取得的 expected，AST 可以识别；对硬编码的 `[2]` 是否来自错误实现，单看代码无法知道生成历史。AI 不能编造来源，只能标为“与已知需求冲突/出处未确认”。

**其他模块负责。** AST 检查自比较/空断言等明显问题，保留实际生成上下文；已有测试运行；受审定输入上的正确/缺陷实现对照；可选变异测试判断敏感性。断言的业务真值来自预先确认规范、独立参考或人工审查，**不是第二个 AI 的认可，也不是 mutation score**。不同“正确实现”是否满足合同先人工审定，不能仅凭它们意见一致证明正确。

**拟新增能力与创新类别。** CoverUp 的已读接受路径主要检查测试可运行与增加覆盖；本作品审查已经存在的测试预期值能否代表需求，并分开“敏感性”和“判定依据”。需求生成 oracle 已有先行论文，故潜在增量只在**现有 AI 测试的审查机制与可复核修正工作流**。一个模型给测试打分、贴“可追溯”标签，或只加变异门槛都不足以创新。

**复用与成本。** 可用 CoverUp 的测试运行/覆盖信息作输入参照，Hypothesis 做样例搜索，mutmut 做可选敏感性检查，本地保存断言与执行版本。优先用库和局部接口，整库 Fork CoverUp 只有在主要目标转为“生成测试”时才合适，本候选并不需要。小筛查约 2～3 人日，完整 Demo 约 12～18 人日。

**最大风险。** 无规范/独立参考时无法判 expected；与 R1 共享需求判定难题，又可能重新卡在材料审核。必须先拿到两个小功能族的明确文档与参考，不让模型补造规范。若只有 AST 一眼能识别的自比较，AI 的作用就不成立。

**最小反证实验。** 选 3 个已审定小函数、每个两个已有/人工设计测试条件，共 6 单元：包含合法快照测试、硬编码错误 expected、明显自比较、关键性质缺失、说明冲突及未知。材料标明真实历史或设计样本，不混算。

强基线：AST 规则＋执行/变异审查；普通 LLM 读相同文档和测试直接审查。指标为错断言检出、有效测试误指控、未知保留、建议是否保持规范、人工改动与审查时间。AI 方法与 LLM 基线最多各 6 次首次输出，不重复生成。**反证：**只能发现 AST 明显问题；强基线同样好；不能审定硬编码 expected；或将无法确认的生成来源说成已证实。此时停止独立 AI 项目，可保留普通测试审查工具。

**评委三问。** 承认 oracle 生成已有；展示一条“高覆盖但 expected 错”的断言及受审定依据，展示把一个合法快照测试保留而非一律删除；现场从绿色测试切到规范冲突，再演示来源未知仍待审。没有独立参考时无法做到最后两步，就不应参赛包装成可信认证器。

### R3 · 失败身份保持的 Bug 复现包生成器

**排序第 3，仅作实用产品备选；当前独立创新 NO-GO。**

**真实问题与场景。** 用户提交长日志或大输入，维护者难以定位稳定复现；AI 缩减脚本后可能只保留另一个无关异常。适合短 Python 字符串/列表处理问题的报告整理，最终输出可复现脚本、缩减输入和环境/版本证据，不自动修复整个仓库。

**Demo 流程。** 用户导入 Bug 描述、代码和输入；AI 提取报告要求的失败症状及相关代码位置，用户确认；worker 验证原始复现；缩减器仅保留满足已确认失败条件与输入前提的结果；导出复现包。比如只读处理不得修改原列表的报告，缩减后必须仍显示列表被修改；另一个更短输入抛 ValueError 不能算复现成功。这个例子未在本轮运行。

AI 做自由报告到结构化失败条件的转换与初始化脚本；程序做真实执行、输入缩减、失败条件判断、版本关联。业务失败身份不是仅比异常名称，无法表达的症状保留待审。复用 Hypothesis 与本地记录；借鉴 MIT SWT-Bench 的评价方法，不搬授权未知的 LIBRO 代码，不引入完整 SWE-bench 环境。

**为何不推荐为创新首选。** LIBRO 已做报告匹配与候选筛选，Hypothesis 已有缩减，SWT-Bench 已做修复前后复现验证。失败条件更严格是合理工程，不足以证明新机制；AI 并不参与经典缩减算法。

**成本/风险与反证。** 小筛查约 1～2 人日，完整局部 Demo 约 7～10 人日；最大风险是失败身份翻译错误和非确定行为。用 3 个报告，其中一个带无关异常陷阱，一个输入有前提，一个症状不明确；比较普通优化 LLM＋相同缩减器以及人工失败条件。若新增层不能减少错误复现或人工工作量，独立创新停止。指标是目标症状保留、无关失败误接收、缩减规模、可重现次数、审核时间，不能用“报错了”作成功标准。

**评委与保留价值。** 可以诚实回答这是成熟方法的面向小项目产品化，不能声称首次自动复现。几分钟内可演示“长输入到短输入，原症状不丢”；即使没有创新增量，复现包整理器仍可能实用。只有用户更看重实用交付时才选它；不与前两名一起开发。

### R4 · 变异反馈驱动的 AI 测试补全台

**排序第 4；NO-GO，不为本比赛另行立项。**

用户已有全绿测试但遗漏边界，工具导入 Python 函数及 pytest，mutmut 列出存活变体，AI 生成补测，程序检查原实现通过、目标变体被检出，再导出测试。几分钟可展示“原测试漏掉 >= 改成 > 的边界，新增测试抓到”；AI 负责读代码与生成测试，程序负责变异、执行和计分。

可复用 mutmut、CoverUp 及本地记录；本地化 Demo 约 6～9 人日，风险是等价变体、错误 expected、测试只针对变体过拟合。最小反证是 3 个函数对照成熟变异提示方法，在相同生成与执行预算下查新增检错与 false positive。

**淘汰原因是直接重合，而非做不出来：MuTAP 已实现存活变体引导生成，CoverUp 已有运行/反馈循环。** 中文报告、网页、版本哈希或增加“Critic Agent”都不够。mutmut 当前需 fork 支持，Windows 要 WSL；接入并非零成本。评委“别人早做过”这一问当前没有有力差异回应，因此不安排上述实验。可作为 R1/R2 的底层可选工具，不独立包装作品。

## 4. 前两名与产品备选的比较

等级是本轮相对判断，不是评分标准或获奖概率。估计按**一名熟悉 Python 与当前项目的开发者、只做本地单人 Demo、2～3 个小业务族**；不含任意仓库、云部署、用户权限与大规模评测。人日估计未实测，模型请求收费取决于后续模型与接口，本文不虚构金额。

| 候选 | 创新潜力 | 已有技术重合风险 | 完整 Demo 可行性 | 开发估计 | 与现有项目兼容性 | 最小验证成本 | 失败后留下什么 |
|---|---|---|---|---|---|---|---|
| **1 R1：意图对齐差分测试** | 中等：允许变化/必须保留的可执行划分，必须证明增量 | 中高：差分、合同、需求 oracle 都既有 | 较高，严格限纯函数；现场对比清楚 | 10～15 人日 | 证据/版本高；执行合同需独立扩展 | 1～2 人日；最多 8 次首次生成＋少量有界执行 | 需求绑定的兼容性/回归审查工具 |
| **2 R2：预期值来源审查** | 中低至中等：可能抓同源自证测试，来源治理不是原创算法 | 高：文档 oracle、测试质量研究直接相邻 | 中等，先有明确规范和独立参考 | 12～18 人日 | 证据/运行设计高；pytest 与参考管理需新增 | 2～3 人日；最多 12 次首次生成＋对照执行 | 带依据与未知状态的测试审查器 |
| **3 R3：复现包生成** | 低，当前没有足够独立机制差异 | 很高：LIBRO、缩减与 SWT-Bench | 较高，只做局部代码，不接整仓依赖 | 7～10 人日 | 运行记录高；新输入/症状合同需新增 | 1～2 人日；原则上先人工/规则检查 | 实用的 Bug 报告整理与复现包 |
| 4 R4：AI 变异补测试 | 低，核心已有 | 极高：MuTAP 直接实现 | 较高，但 Linux/WSL 与测试环境要适配 | 6～9 人日 | 部分；变异测试流水线另建 | 本轮不建议投入 | 普通测试生成器，竞争差异弱 |

**排序理由。** R1 的“合法改变不该报错、意外改变必须抓到”天然形成两类相反的可检验错误，现场解释短，且不是追问与学习效果研究。R2 的问题也真实，但需要证明预期值的依据，材料和审核更重；优先级低于 R1。R3 交付较稳，却难回答新颖性质疑，作为实用备选而非高分创新承诺。没有为凑五个项目再列一个泛化 Agent。

前两名共享需求与执行组件，但应**择一**验证，不能合成大平台后把两个待证机制相加。若 R1 的意图翻译都不能可靠成立，不应马上换名继续 R2。

## 5. 几分钟现场演示需要满足的条件

R1 的目标展示顺序：

| 时间预算 | 操作 | 应呈现的证据 |
|---|---|---|
| 0:00～0:40 | 打开旧版本、新补丁、明确变更条款 | 条款出处；哪些行为允许变、哪些必须保留 |
| 0:40～1:30 | 发起一次分析或查看已标明的预计算映射，确认要求 | AI 只提出候选条件；确认与待定状态可见 |
| 1:30～2:40 | 真实执行一条新输入，再看缩减反例 | 两个版本的任务 ID/哈希/输入/输出；允许差异与回归分开 |
| 2:40～3:30 | 换正确补丁，重跑同一验证条件 | 错误结论撤销；失败/未知保留；导出可执行测试 |

这是未来演示预算，不是已经验证的响应时间。[V2 历史限制](<../old-ui/v2/V2_limitations.md>)记录一次 AI 回复约 130 秒；当前 Provider 说明也没有真实外部 API 联通验收。因此不能承诺连续多次实时生成仍在三分钟内完成。

后续应将一次语义生成与确定性验证分开。预计算的 AI 输出必须明确标记回放；现场至少一条新输入使用真实受限执行、准确版本，不能把旧日志冒充新运行。如果比赛要求全程实时 AI，就先测所选接口时延，再决定能否满足；没有核实规则前不编造要求。缓存、单次生成或换传输是演示工程，不属于创新证据。

R2 可用“全绿→发现 expected 与规范冲突→保留合法测试/未知”展示；R3 可用“缩减后仍是原症状，拒绝无关异常”展示。它们都应展示失败边界，不能只显示一个精彩成功案例。

## 6. 用户选定第一名后，最先做什么

**本轮不执行。** 后续只验证 R1 的一个问题：

> 在相同需求、代码、搜索和模型预算下，意图约束的差分机制是否比优化普通 LLM＋成熟差分工具，更准确地区分合法变化与需求外回归，或保持准确而减少人工形式化成本？

先准备受审定需求与版本，不开发网页。四个任务中保留正确补丁与未知意图，避免所有样本都需要“抓错”。参考规范与判定由开发者事前确认，运行事实由执行器检查；不用第二 AI 给语义结论盖章。

先做不需要模型的合同/输入/参考检查，再做少量首次模型输出与同预算强基线。出现无法审定的业务合同、错误放行或普通基线无差异时立即停止，不增加 Agent 或反复调 Prompt 找最优结果。若有可复核增量，才允许讨论独立 worker 与完整 Demo，不能从“一个设想很合理”直接进入产品开发。

## 7. 最终决定与本轮边界

**产品方向：转换成聚焦的编程验证工具。** 通用学习台保持现状，保留为已有工程成果与未来工具可复用的界面/证据组件；不再以它的功能累积支撑独立创新。教育场景可以作为“学生开发者也会用”的用户入口，不要求测知识掌握或迁移效果。

- **首选 R1：CONDITIONAL GO，仅小规模机制验证。**
- **次选 R2：CONDITIONAL GO，先确认规范与独立参考材料，作为替代而非并行工程。**
- **R3：实用产品备选；当前独立创新 NO-GO。**
- **R4：NO-GO，采用成熟工具能力即可。**

这份筛选没有证明已经找到独创算法，也没有证明项目能够获奖。它给出两种比继续教学平台包装更值得反证的具体工具形态。若第一名不能胜过强基线，应降低创新预期或停止该选题，而不是把普通执行记录再次改名。

本轮完成的是既有报告/源码复核、针对新方向的必要开源检索和一份选题报告。没有原型、教学模型请求、双 AI 评分、沙箱任务、外部 Fork、安装或现有系统修改。后续工作等待用户选定候选。
